# Demos whose geometry is not gated, and why.
#
# One id per line, then a reason. A demo is on this list because something
# other than the feature under test decides its rectangles, and a gate that
# included it would be red for something nobody can fix by fixing that feature.
#
# Every line here is a debt, not an exemption. The reason is the thing to go
# and remove, and the list only ever shrinks on purpose.
#
# ------------------------------------------------------------------------
# It used to be twenty-four, and every one of them said `font`
#
# areole drew with its own bitmap face and a browser drew with whatever
# `sans-serif` resolved to, so any box sized by words differed by the
# difference between two fonts. That is gone: `tools/gen_gallery_font.py`
# converts font8x8 -- public domain, and already the face areole draws with --
# into TrueType, and every demo inlines it. Thirteen of the twenty-four went
# green the moment both engines were drawing the same outlines.
#
# What is left is ten demos under six causes, each named below, and none of
# them is the font any more. `css/text/line-height` came off a second time when
# the line-box compounding was fixed, and three more came off when line boxes
# got the strut they were missing.

# ---- fractional lines and fractional margins ---------------------------
#
# A browser lays out in 1/64ths and rounds every number it reports on its own.
# This engine is integers all the way down, so `line-height: 1.4` at 16px is
# 22.4 there and 22 here: six lines of a paragraph are 134 and 132. The `em`
# margins between headings are the same arithmetic from the other end -- h1
# through h5 agree box for box, and by h6 the discarded fractions are worth two
# whole pixels.
#
# This is the residual the table corpus is also down to, and the only one on
# this list that integer geometry cannot reach rather than merely has not
# reached yet.
#
# (What used to be here: five demos with no strut. A browser's line box is at
# least as tall as the containing block's own font would make it whether or not
# any text is on it -- CSS 2.1 10.8.1, a zero-width inline box carrying the
# block's font, whose ascent and descent join the maxima like any item's. This
# engine's line was only as tall as the tallest thing actually on it, so a line
# holding one inline-block was short by the font's descent, and so was the last
# line of every paragraph. `css/display/inline-block`, `html/parsing/foreign-svg`
# and `html/parsing/cdata` are green; the two below stayed for the reason above,
# which was underneath the strut and is not the same thing.
#
# Finding it took a second fix, because the browser's number was wrong too. A
# demo built out of empty boxes never puts a glyph on the page, a browser
# fetches a web font only when a glyph needs one, and the browser was therefore
# measuring its strut against whatever font it had found -- reporting 36 for a
# line both engines put at 33. `_font.css` now carries one hidden character to
# force the load, which is rule 4 enforced instead of assumed.)

css/text/wrap            engine: integer line boxes, so six lines of 22.4px are 132 and not 134
html/elements/headings   engine: integer `em` margins, accumulating to two pixels by h6

# ---- a media feature this engine answers for itself ---------------------
#
# Not a disagreement about media queries. A disagreement about the machine,
# and in two of the three cases a permanent one that is the whole point of the
# feature:
#
#   scripting      Chrome runs scripts. areole never will, and
#                  `@media (scripting: none)` is how a page says what to do
#                  about that. If this demo ever agreed, something broke.
#   display-mode   Chrome is a browser tab. areole is an application.
#
# The third is pending rather than permanent: `prefers-color-scheme` is wired
# to the OS at 0.16.1 and reports its documented default of `light` until
# then. The headless browser this corpus runs against reports `dark`, so the
# two pick opposite branches -- correctly, each about itself.
#
# These are gated on their syntax by tools/compare_media.py instead, which
# agrees with Chrome on 624 of 624 queries because it asks only about the
# features both engines answer the same question about.

css/media/scripting-none        engine: scripting is none here and enabled there, permanently
css/media/display-mode          engine: an application is not a browser tab, permanently
css/media/prefers-color-scheme  engine: the documented default is light until 0.16.1 wires the OS

# ---- there is one face, and it is neither bold nor italic ---------------
#
# `ar_font_load_styled` exists and the gallery renderer loads no styled face,
# so `<b>` and `<i>` are drawn in the one face there is, with its advances,
# while a browser synthesises a heavier and a slanted one and gets wider ones.

css/text/weight          engine: no bold or italic face is loaded, so their advances are the roman ones

# ---- a border reserves no space ----------------------------------------
#
# `ar_used_size` gives a border no room, here and everywhere. An `<hr>` is
# nothing *but* a border, so it comes out zero pixels tall where a browser
# gives it two.

html/elements/hr         engine: a border reserves no space, and an hr is only a border

# ---- half-pixels -------------------------------------------------------
#
# The same ones the table corpus has left. A browser splits a collapsed line
# into halves it can hold and this engine cannot: 303 where a browser says
# 300, from columns each half a pixel out.

css/table/collapse       engine: half-pixels, the same ones the table corpus has left

# ---- values this engine does not have ----------------------------------

css/display/contents     engine: a display:contents box still has a rectangle here, and generates none in a browser
html/elements/pre        engine: `font-family: monospace` is 0.2.1, so pre is drawn in the one face there is

# ---- a face that states no metrics --------------------------------------
#
# `ex`, `ch`, `cap` and `ic` are metrics a font supplies, and areole draws
# these demos with its built-in bitmap face, which is not a TrueType file and
# carries no OS/2 table to state them in. So this engine takes the fallbacks
# CSS names -- half an em for ex and ch, seven tenths for cap -- while the
# browser reads the real numbers out of the gallery face.
#
# The gallery face is a transcription of that same bitmap design and states
# them truthfully: sxHeight 512 and sCapHeight 640 of 1024, so a cap is
# 0.625em where the fallback guesses 0.7, and "0" advances a whole em where
# the fallback guesses half of one. Both engines are right about the face
# each can see.
#
# `css/units/ex` is **not** on this list and that is a coincidence worth
# knowing: the face's x-height is exactly the half em the fallback assumes,
# so the two agree by arithmetic rather than because areole read anything.
# It would come off the moment the design's x-height changed.
#
# The fix is not a units fix. It is for areole's built-in face to carry the
# metrics it has always had, or for the gallery renderer to load the TrueType
# twin the browser is already given.

css/units/cap            engine: the built-in face states no cap height, so 0.7em is the fallback rather than the design's 0.625
css/units/ch             engine: the built-in face states no advance for "0", so half an em is the fallback rather than the design's whole one

# ---- a percentage padding is read as pixels ------------------------------
#
# **This one is a bug and not a difference.** `padding: 10%` is stored with
# its unit and then read as a raw number by every one of the fourteen places
# that want a padding, so ten per cent of a 400px containing block comes out
# ten pixels. `width` and `height` resolve their percentages correctly, which
# is why the first two boxes of that demo agree and the last two do not.
#
# It is 0.4.1's fourth acceptance criterion and 0.4.1 did not meet it. The
# reason it was not fixed with the units is that it is not a units change:
# block flow, flex, grid and the table each resolve sizes in their own code,
# there is no one place a padding becomes a number, and all four are the
# hottest loops in the engine. Doing it properly also means deciding what a
# percentage padding contributes to an intrinsic size, which CSS answers with
# zero and this engine has no path for.
#
# The demo stays, red, because it is the thing that will go green.

css/units/percentage-references  engine: a percentage padding is read as pixels -- see 0.4.1's stated debt
